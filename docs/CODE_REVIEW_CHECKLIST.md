# 代码评审 Checklist（团队统一口径）

> 评审不是找茬，是让代码"可维护、可协作、质量可控"。提交前作者先自查，评审人再据此逐条过。
> 配合 `.github/pull_request_template.md` 使用。

## 1. 正确性 / 功能

- [ ] 改动确实解决了描述的问题，没有引入回归
- [ ] 边界情况被处理（空值、空列表、超长输入、首屏无数据）
- [ ] 异步/竞态被处理（组件卸载后不再 setState、请求竞态有保护）

## 2. 类型安全

- [ ] 没有用 `as` 硬转类型绕过检查（确有必要时加注释说明为什么安全）
- [ ] 没有用 `any` 逃避类型（库类型缺失时优先补 `declare`/`type` 而非 `any`）
- [ ] 导出的函数 / 组件 props 有显式类型签名
- [ ] 接口字段与后端（Rust 命令）实际返回一致

## 3. 错误处理（本项目的重点短板）

- [ ] 没有裸 `.catch(() => {})` 静默吞错
- [ ] 用户可感知的失败有 toast / 日志；异常有上下文信息
- [ ] 网络 / IO 调用（Tauri `invoke`）失败路径被覆盖

## 4. 结构与可维护性

- [ ] 单一组件 / 函数职责清晰，巨型组件（>300 行）已考虑拆分
- [ ] 纯逻辑（工具函数、状态计算）与 UI 分离，便于单测
- [ ] 魔法数字 / 硬编码字符串已提取为常量或配置
- [ ] 命名自解释，无缩写歧义

## 5. 可测试性

- [ ] 纯函数（如 `fuzzyMatch`、`fmtTime`、`resolveMode`）已抽离并可单测
- [ ] 新增逻辑补了测试（Vitest）
- [ ] 组件副作用（事件监听、定时器）有清理

## 6. 性能 / 体验

- [ ] 列表渲染有稳定 `key`（优先业务 id，而非数组下标）
- [ ] 不必要的重渲染被避免（`useMemo`/`useCallback` 用得其所）
- [ ] 用户输入 / 滚动等高频路径无明显卡顿

## 7. 安全 / 健壮性

- [ ] 不直接拼接用户输入进命令 / SQL / 路径
- [ ] 渲染用户内容注意 XSS（React 默认转义，勿用 `dangerouslySetInnerHTML`）

## 8. 提交规范

- [ ] 提交信息清晰（动词开头：add / fix / refactor / chore）
- [ ] 一个提交一个关注点，不混搭功能与格式化
- [ ] 格式化由 Prettier 统一，不手动调缩进
